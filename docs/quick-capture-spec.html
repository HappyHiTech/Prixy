Quick Capture with AI parsing

The user types a messy note and taps Save. Claude splits it into separate prayer requests, tidies the wording, and links each one to an existing prayee and category when the match is clear.

Design approved Branch: feat/quick-capture 2026-10-03 Source of truth: quick-capture-spec.md

requestTextPrayeeCategoryStatus

Why one went to the InboxYour existing rule: a request is active only when both prayee and category are set. Claude leaves a field empty unless it's sure, so anything uncertain lands in the Inbox for you to review.

How it flows

From tapping Save to seeing the new cards on Home.

1
User taps Save Frontend
The button shows a spinner and is disabled, so a double tap can't create duplicates.
2
POST /prayers/capture { text } API Gateway
The Cognito authorizer verifies the token and passes the user's sub.
3
Load the user's prayees + categories RDS
Look up user_id, fetch both lists as id: name, then release the DB connection. Don't hold a connection open while waiting on the AI.
4
Ask Claude to split + match Bedrock
Goes through the private VPC endpoint. Structured outputs force a fixed JSON shape: { requests: [{ requestText, prayeeId, categoryId }] }.
5
Validate in code Lambda
Any id that isn't in the user's own lists becomes null. Empty items are dropped. A capture creates at most 20 requests.
6
Insert all rows in one transaction RDS
The status rule is applied per row. If any insert fails, nothing is saved.
7
Back to Home Frontend
Reset the text, router.back(). TanStack invalidates ['prayerRequests'], so the lists refetch on their own.

Decisions

What was decided and why, so it doesn't get re-argued later.

D1 · ScopeSplit, clean, and match to existing prayees + categoriesNever creates new ones. That avoids duplicates like "Mom" vs "my mom".
D2 · SyncOne request, one responseAn LLM call takes seconds. Voice is async only because Transcribe is slow.
D3 · NetworkBedrock through a VPC interface endpointThe Lambda is in the VPC (for RDS) with no internet route. IAM auth, so there's no API key to store. Much cheaper than a NAT gateway.
D4 · Endpointbedrock-runtime, not MantleIt supports structured outputs and has a known VPC endpoint service.
D5 · ModelClaude Haiku 4.5, no thinkingSonnet 5.5 was the first pick, but this account has 0 quota for the Sonnets. Haiku is fast and cheap (~$0.0016/capture). Swapping later is one env var plus re-adding thinking/effort.
D6 · StatusThe existing Inbox → Active rule applies unchangedOne rule everywhere. Cautious matching sends uncertain requests to the Inbox.
D7 · FailureFail cleanly, save nothingThe text stays on screen, so the user just retries. No silent fallback that hides a broken AI step.
D8 · raw_transcriptHolds the AI's cleaned textSame meaning as on the voice path: "what the AI wrote, before user edits".
D9 · PrivacyRaw typed input is not storedNothing reads it, and prayer content is personal.
D10 · ReuseShared parseRequests + insertRequestsThe voice pipeline plugs into the same code later.
D11 · UXStraight back to Home after savingFastest. A toast is a cheap follow-up if needed.

API contract

POST /prayers/capture · Cognito auth · body { "text": "..." }

StatusWhenBody
201At least one request createdPrayerRequest[]
400Text missing, empty, or over 5,000 characters{ message }
401No Cognito sub{ message }
404No user row for this sub{ message }
422The AI found no prayer request (e.g. "asdf"){ message }
502Bedrock failed: throttled, timed out, no model access, or bad output{ message }
500Anything else (DB errors){ message }
Messages are user-facingThe frontend's ApiError already shows the server's message, so write them for the user to read.

The handler, step by step

  1. No sub → 401
  2. Parse and validate text → 400 if bad
  3. DB: find the user (404 if none), load prayees + categories, release the connection
  4. parseRequests(): if it throws → 502; if it returns [] → 422
  5. DB: insertRequests(client, userId, splits, 'manual')
  6. 201 with the array

Calling Claude

Request settings
modelprocess.env.BEDROCK_MODEL_ID
max_tokens2048
output_configJSON schema only
SDK timeout10s, 1 retry (20s worst case < 25s Lambda)
Haiku 4.5 notesNo effort (Haiku rejects it) and no thinking (leaving it out turns thinking off). Model ID: global.anthropic.claude-haiku-4-5-20251001-v1:0. The bare ID fails because Haiku only supports inference profiles.
Prompt rules
  1. One request per distinct person or need
  2. Clean up the wording in the user's voice. Never add details.
  3. prayeeId only on a clear match, otherwise null
  4. categoryId only if one clearly fits, otherwise null
  5. Only use ids from the lists given
  6. No prayer request in the text → { "requests": [] }
Output JSON schema 
{
  "type": "object",
  "additionalProperties": false,
  "required": ["requests"],
  "properties": {
    "requests": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["requestText", "prayeeId", "categoryId"],
        "properties": {
          "requestText": { "type": "string" },
          "prayeeId":    { "type": ["string", "null"] },
          "categoryId":  { "type": ["string", "null"] }
        }
      }
    }
  }
}

Check stop_reason before parsing. Anything other than end_turn (for example max_tokens or refusal) is an error → 502.

validateSplits: the safety net

  1. raw.requests isn't an array → throw (becomes a 502)
  2. Trim requestText; drop the item if it's empty
  3. Ids not in the user's lists → null
  4. Keep at most 20 items
This is the security boundaryWhatever the prompt says, the model can never attach a request to an id it invented or to another user's record. It's a pure function, so it's the part with unit tests.

What gets inserted

ColumnValue
request_textAI's cleaned text
raw_transcriptSame AI text, never edited afterward

Infrastructure

Changes to backend/infra/template.yaml.

The core AWS ideaYour Lambda lives in a private network (VPC) with no road to the internet. A VPC interface endpoint adds a private road to one AWS service, Bedrock. With PrivateDnsEnabled, the normal Bedrock hostname points down that road automatically, so the SDK code doesn't change.
BedrockRuntimeEndpoint

AWS::EC2::VPCEndpoint

  • Type Interface
  • com.amazonaws.${AWS::Region}.bedrock-runtime
  • One subnet (one AZ ≈ $7/mo)
  • PrivateDnsEnabled: true
BedrockEndpointSecurityGroup

AWS::EC2::SecurityGroup

  • Inbound TCP 443 from the Lambda SG sg-0e9a…eac2
  • The Lambda SG must allow outbound 443
CapturePrayersFunction

AWS::Serverless::Function

  • Timeout: 25 (under API Gateway's 29s)
  • Same VPC config + DB env as the others
  • + BEDROCK_MODEL_ID env var
  • + bedrock:InvokeModel on this model only
  • POST /prayers/capture, CognitoAuth
YAML anchor gotchaThe *dbEnvironment and *dbPolicies anchors can't be extended with an extra entry. Write Environment and Policies out in full for this function.

When things go wrong

Every failure either saves nothing or quietly makes a safe choice.

FailureUser seesSaved?
Empty or too-long text400Nothing
Bedrock down, throttled, no access, endpoint misconfigured502 "Try again"Nothing
Model output truncated, refused, or malformed502Nothing
No prayer request found422Nothing
Model invents an idNothing visible. The id becomes null → InboxRows saved
DB error mid-insert500Nothing (rolled back)
Logging ruleLog error types, messages, and Bedrock request ids. Never log the user's text or the model's output, because both contain personal prayer content.
